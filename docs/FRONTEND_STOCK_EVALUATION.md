# Actual frontend stock forecast benchmark

This benchmark tests the **same browser TypeScript functions the shipped React app uses**. It does not implement a second XGBoost, LightGBM, VARMA, Chronos, or Ridge engine. Models and training parameters are imported from `frontend/app/src/core.ts`, `lightgbm.ts`, `varma.ts`, `chronos.ts`, and `ridge.ts`, served by the local Vite dev server and executed in real Chromium via Playwright.

## Method

- Data: existing `data/stocks/multivariate.csv` generated by `backend/fetch_stock_groups.py`; market-calendar date, one fixed group target and **all predeclared domestic sector peers**, all observed Close values. No macro/foreign feature is included. VARMA requires at least two numeric series.
- Groups: the five **predeclared** `config/stock-evaluation-groups.json` groups; no selection using test scores.
- Two 16-step windows: the most recent **16 completed market sessions** and the **preceding 16 sessions**, tested as separate nonoverlapping holdouts. At each origin, training sees **256 observations before the origin**; never pass holdout rows to the frontend functions.
- **Rolling 1-step evaluation:** refit each real frontend model at **32 successive origins** (the latest 32 completed market sessions) for every predeclared group. Every origin receives exactly the **256 prior observed sessions** of the target and all domestic peers. Hold out its next completed market session, predict **only that one value**, compare against that day's actual close. It never fabricates future peers, since all inputs at each next-day origin are observed historical prices.
- The rolling series overlaps the two 16-session windows. It is a different forecasting protocol, not additional independent market observations. The 32 origins share training data and model states (for Chronos, pretrained weights).
- Forecast: real UI `trainModel`+`forecastNextN`, `trainLightGBMModel`+`forecastNextN`, `trainVarmaModel`+`forecastVarmaNextN`, `forecastChronosNext16` (pretrained), and `trainRidgeModel`+`forecastNextN` on the **same input structure**. The 16 returned values are aligned by market-session index with the next 16 actual closes. The app's calendar-based labels are not used to align trading days.
- Metrics: MAE (price units), MAPE, 1-step and 16-step absolute percentage errors, and direction hit relative to the known last close at forecast origin. Naive baseline repeats that close across all horizons. Baseline direction is N/A.
- Reporting: 5 groups × 2 holdouts × 5 models = **50 required 16-step results**, plus 5 groups × 32 daily origins × 5 models = **800 required rolling one-step results** (total 850). A failure prevents writing/committing either official JSON or README. No quietly omitted models and no invented results. Every date is re-evaluated; no cherry-picking.
- Charts: five SVGs showing actual prices versus all five forecast paths and the fixed-origin last-close baseline for the latest 16-step holdout; one SVG of the mean absolute percentage error by horizon across the five groups. All six are rendered from validated, numerical, model-generated report data and linked in README.

## Important caveats

This is **retrospective holdout evaluation** on later-retrieved prices, not a real-time timestamped prediction audit. Historical bars may be revised. The old feature generator included the same-row target in cross features while fitting the model. It now uses only observations through t-1 to predict target[t], and tests verify that the feature row at a historical origin matches true next-step inference on that prefix. This changes the model and invalidates pre-fix scores. The browser app defaults to the direct 16-step strategy for XGBoost, LightGBM and Ridge, while this scheduled benchmark intentionally evaluates their recursive mode for historical continuity. No fixed seasonal blend is applied. Older blended benchmark results are not directly comparable. Avoid inferring causal predictive power, investability, or trading P/L from these metrics. VARMA is explicitly experimental.

The separately maintained legacy benchmarking scripts also no longer apply a fixed seasonal prediction blend; previously published scores from those scripts require a fresh evaluation before comparing.

The existing daily `evaluation.yml` performs a different, legacy stock experiment with its **own** Ridge implementation and differently configured ML models. Its `<!-- STOCK_MULTIVARIATE:START -->` README section is preserved and explicitly labeled **Legacy separate-engine stock benchmark** after the first real-frontend run. The new workflow runs later and writes an independent `<!-- FRONTEND_STOCK_EVALUATION:START -->` block.

## Execute locally

From the repository root:

```bash
# Ensure downloaded stock bars exist; use your own UID to prevent root-owned outputs.
LOCAL_UID="$(id -u)" LOCAL_GID="$(id -g)" \
  docker compose run --rm --build backend

node --test scripts/frontend-stock-evaluation-core.test.mjs

# This starts the REAL Vite app and a headless browser running its frontend code.
LOCAL_UID="$(id -u)" LOCAL_GID="$(id -g)" \
  docker compose -f docker-compose.yml -f docker-compose.frontend-evaluation.yml \
  up --build --abort-on-container-exit --exit-code-from frontend_stock_eval

# Optional cleanup after completion
LOCAL_UID="$(id -u)" LOCAL_GID="$(id -g)" \
  docker compose -f docker-compose.yml -f docker-compose.frontend-evaluation.yml down
```

Chronos-2 needs access to the existing Hugging Face ONNX model URL and the ONNX Runtime WASM CDN (as does the actual UI). If a model cannot run, **the workflow fails** and leaves the previous published results intact. The first full run may be slow; subsequent runs still retrain/re-evaluate to reflect current frontend code.

## GitHub Actions

Push the files to `main`, then run `gh workflow run frontend-stock-evaluation.yml --ref main` once to validate all five models on GitHub's Chromium runner. Once validated, the schedule starts at **19:23 JST daily** (UTC 10:23; GitHub schedule can be delayed). A new market day updates the generated README block, `reports/stocks/frontend-evaluation.json`, and six SVG files in `reports/stocks/charts/`. On a closed market day, the observed session date does not change; reruns may update the evaluation timestamp. The legacy scheduled workflow remains active until explicitly disabled after the new workflow is seen to succeed.

Inspect failures with `gh run view --log-failed`; especially verify ONNX runtime model retrieval, WASM support, and RAM/time budget. Do not interpret `success` until the README shows the new "Real frontend stock forecasting benchmark" section. Historical scores in the legacy block are not comparable to this protocol.

## Comparing results fairly

The **last-close** baseline is a 16-step forecast at a single origin, repeating
that origin's closing price across the full horizon. It does **not** obtain
future daily closes. This is a valid strong random-walk baseline for asset
prices, not an implementation error. Each 16-step model forecast is compared
against those 16 sessions, by market-session position rather than app-generated
calendar labels (which need not match exchange holidays).

The benchmark sends the browser the latest 256 **prior** closes of the target
and all predeclared domestic sector peers, with no macro indicators. It measures
unblended recursive forecasts for the three supervised regressors. The UI
instead defaults to direct 16-step forecasts, so the benchmark is NOT a measure
of that default strategy. Variations in accuracy may arise from recursive
forecast drift or imputed future peer prices, not necessarily from tree/linear learning.
The two windows cover just 32 sessions and do not prove a systematic edge.

## Why not predict all series with one model?

`forecastNextN` is the shipped frontend's rollout of a **target-only one-step regressor**. For 16 steps it must predict new observations or otherwise populate the future peer rows. At horizon 1, `forecastNextN(..., 1)` uses **only observed last-day inputs**, so its one-step error is not caused by peer extrapolation. The benchmark uses the real frontend function, not a new model. Chronos-2 supplies 16 direct forecasts and rolling uses only the first; VARMA already performs **joint multi-series autoregression** and rolling evaluates its first forecast.

A new coupled XGBoost/LightGBM/Ridge approach could fit one target model **per column**, predict all peer values simultaneously at each future step, and feed the newly predicted vector into the next step. But the original algorithms are single-output and cannot automatically turn into a joint multi-output learner without an explicit method. Such a coupled rollout would change the shipped UI and deserves a distinct, separately evaluated variant. We do not add that variant before measuring the existing models' 1-step accuracy.

### Interpret the results

- If rolling 1-step MAPE is competitive but 16-step MAPE is poor, suspect recursive drift or predicted future peer values; it does **not** prove the trained regressor is intrinsically poor.
- If rolling 1-step MAPE still loses to the previous observed close, inspect target/feature scaling, model bias, and data timing before introducing a joint peer forecast.
- A shared one-step training set and 32 overlapping refits do not provide 32 independent statistical samples. Claims of trading profitability, causality, or live forecasting performance require a separate time-stamped prospective evaluation.
- All outputs are plotted against completed market dates, not against guessed calendar labels; exchange holidays are handled by the historical index.

## Matched Direct 16-step price vs log-return experiment

This is an **on-demand** heavy benchmark, separate from the daily 850-result
recursive benchmark. First run the standard benchmark with the same stock CSV,
then run:

```bash
export LOCAL_UID="$(id -u)" LOCAL_GID="$(id -g)"
docker compose -f docker-compose.yml -f docker-compose.direct-evaluation.yml \
  run --rm --build frontend_direct_eval
```

The real browser implementation trains a distinct XGBoost, LightGBM or Ridge
model for every one of the 16 horizons, for both absolute price and **cumulative
log return**. Evaluation covers 5 fixed stock groups x 2 disjoint 16-session
holdouts x 3 models x 2 target representations = **60 full 16-step forecasts**
(960 independently fitted horizon models). This can take significant CPU time,
especially for XGBoost/LightGBM. No synthetic data or missing future peer values
are used in the direct features. All 3 strategies use the same 256-observation
training windows for each target, but Direct horizon h has fewer labeled pairs
than recursive one-step, because the last h future labels do not exist.

The experiment requires `reports/stocks/frontend-evaluation.json` to match the
current source data fingerprint. It writes
`reports/stocks/direct-comparison.json` and adds only a compact three-row MAPE
comparison table to README, with no new charts or methodology prose. The daily
stock benchmark suppresses a stale Direct table if its market data or protocol
fingerprint changes. These are retrospective historical evaluations, not live
or point-in-time trading predictions. Assess model accuracy before choosing
whether to change the UI's default target mode.
